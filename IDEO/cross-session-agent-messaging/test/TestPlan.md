# 双向会话通信测试方案

状态：T01–T05 已完成当前原型的证据映射。首次联系、双向空闲/工具边界、Codex 生成末尾 Stop 接续和连续往返有通过证据；Claude 纯模型生成期间收信经五次 explicit 采样判定为严格失败。当前原型不能宣布完整基础通信目标全部通过。

依据：[TargetMap](../TargetMap.md) 的 Goal、选定 Questions 与接收规则，以及[研究实验记录](../../deep-research/experiments-2026-09-06.md)中仍需验证的缺口。此方案与 Ideate 并行准备，供不同候选方案使用共同的行为判据。

## 1. 验证目标与边界

本轮验证：Codex 与 Claude Code 能否找到选定的对方现有会话，按约定时机双向送达消息，并在原会话中接续对话，全程无需 PO 搬运消息。

| 验证内容 | 对应问题 | 对应场景 |
|---|---|---|
| 找到并准确指定对方原会话 | Q1：会话识别 | T01；所有场景均核对会话身份 |
| 空闲及工作中按约定获知消息 | Q1：送达与接收 | T02、T03、T04 |
| 请求、回复、追问连续往返 | Q3 的通信部分 | T05 |

“原会话”是测试开始前已选定且正在运行的那两个会话。分叉副本或替代会话收信、应答不能作为通过依据。底层采用文件、队列或其他媒介均可，判定依据是原会话实际发生的行为。

反馈质量、完整开发任务交付和长期减负效果仅作观察。产品回执、失败处理、会话变化后的寻址维护、来源校验等尚未决定的范围项，不在本方案中擅自新增或排除；如后续纳入本轮，由对应需求补充场景。

## 2. 共同前提与证据

### 测试准备

- 记录候选方案及原型版本、两端工具版本、运行方式、关键配置和项目位置；结论只适用于所记录条件。
- 使用真实工具中预先运行的两个会话，记录能区分它们的身份信息。按候选方案提供的方式建立联系，保留对象选择与身份对应的证据。
- PO 可以启动会话、完成方案要求的初始配置、发起测试任务和观察结果；测试消息及回复由会话通过候选通信方式发送。
- 各次投递使用独特标记和简短正文。具体标记仅经待测通道传给接收方，避免从准备指令或其他途径提前泄露给它。
- 串行执行场景；尽量保持消息内容形式、环境和原型配置一致，一次改变方向或接收状态，便于解释结果。这遵循 Identify a Variable 方法的思路。

方向 A 为 Claude Code 发起、Codex 接收；方向 B 为 Codex 发起、Claude Code 接收。所有场景覆盖两个方向。

### 必须能够观察的事实

| 事实 | 需要的证据 | 单独不足以证明的材料 |
|---|---|---|
| 联系到了正确对象 | 发送前选定的会话身份，与实际收信及回应所在会话的对应关系 | 显示名称相同、模型声称自己是某个角色 |
| 消息进入了会话 | 原会话输入或事件记录中出现本次消息；必要时结合接收方对独特标记及正文的回应 | 发送命令成功、写入队列或文件成功 |
| 空闲时由消息触发调用 | 消息到达前的空闲状态、消息到达及随后调用的记录，期间无人工输入促成接收 | 手动输入新提示后模型才读到消息 |
| 工作中按边界接收 | 消息到达、当前模型调用及相关工具结束、紧接着的下一次调用输入之间的时序关系 | 稍后最终回复、模型自行声称收信时机正确 |
| 连续往返保持在原会话 | 双方原会话中可对应的请求、回复、追问和再次回复记录 | 由 PO 或旁路脚本将答复抄到另一会话 |

取证方式可以随原型变化，但须在测试前明确。调用输入、会话事件或其他等效记录无法展示必要事实时，相关判据记为“无法判定”，不以源码推断替代实际结果。

应区分发送、接收侧接受消息、模型获得消息上下文和发出回应。开测前根据候选接口确定这些事件的可观察含义。测试不要求产品提供已送达或已读回执。

## 3. 场景与判据

| 编号 | 接收方前置状态 | 操作 | 通过条件 |
|---|---|---|---|
| T01 首次联系 | 原会话已运行，身份可核对 | 按候选方案的识别与指定方式联系对方，发送带独特标记的消息，请其回应 | 收信者是选定原会话，正文到达；回应返回原发起会话。可与首次 T02 共用运行证据 |
| T02 空闲收信 | 当前没有模型调用或工具执行，正在等待新刺激 | 发起方发送消息，明确请求回传标记；接收方不接受额外人工输入 | 消息触发原接收会话的新调用，模型获得正文；后续回应能通过候选方式返回原发起会话 |
| T03 模型生成期间收信 | 接收方正在一次可观察的模型调用中 | 在该调用尚未结束时投递消息，并确认消息到达接收入口的时间 | 当前调用及其触发的工具执行正常完成；消息在紧接着的下一次模型调用前加入上下文，没有为了注入消息而强制中止或切换原任务 |
| T04 工具执行期间收信 | 接收方正在执行当前模型调用触发的工具 | 在工具执行期间投递消息，并确认消息到达接收入口的时间 | 当前工具执行正常完成；消息在随后第一次模型调用前进入上下文，没有为了注入消息而中断工具或强制切换原任务 |
| T05 连续往返 | 两个原会话均保持运行，单次收发路径已可用 | 本次方向的发起方提出简短请求，对方回复；发起方依据回复继续追问，对方再次回应 | 各轮消息能与本次交流对应，始终发生在选定原会话之间；无需 PO 转述或替任一方输入对端消息 |

### 场景执行约定

- T03、T04 使用可重复、能够观察开始和结束的工作。具体任务及投递时机随原型补充；如果没有捕捉到规定的忙碌窗口，本次不能用于判定该状态的接收行为。
- “工作中收信”的边界是相邻模型调用之间，原任务可以尚未完成。消息在更晚的调用中才被看到，不能替代对紧接着下一次调用的核对。
- 接收方获得上下文后可以自行安排处理。忙碌场景不以“立刻答复”为通过条件；连续往返场景通过明确的测试请求观察回应。
- 每次运行记录接收和回应所用时间。当前未约定响应时长上限；研究中的轮询间隔或延迟估计不自动成为验收标准。观察窗口在运行前约定，超出窗口但原因不明时记录事实和证据缺口。
- 先核对会话身份及基本链路，再完成各状态与多轮场景。早期实验可以只检查一个缺口，但单格成功不能表述为整个 Target 已通过。

## 4. 结果判定与记录

| 状态 | 含义 |
|---|---|
| 未执行 | 尚无本场景的实际运行记录 |
| 通过 | 前置条件成立，要求的行为已发生，证据足够 |
| 失败 | 前置条件成立，观察到违反要求的行为，例如副本取代原会话参与、指定接收边界被错过或消息正文丢失 |
| 无法判定 | 状态窗口未捕捉到、关键证据缺失，或环境故障使本次运行不足以说明候选行为；注明原因 |

比较候选时使用相同判据，并说明环境差异。同一候选组合与版本完成全部适用场景、两个方向都有充分的通过证据后，才据此判断本轮基础通信目标是否满足。该结论不等同于长期可靠性或所有使用环境均已验证。

实际结果集中记录在本目录后续建立的 `TestResults.md`，每次运行至少包含：场景编号与方向、候选及版本、会话身份、前置状态、操作与消息标记、观察窗口、实际时序与正文、证据位置、结果及限制。

| 场景 | 方向 A：Claude → Codex | 方向 B：Codex → Claude |
|---|---|---|
| T01 | 通过：P06 准备消息与身份对应 | 通过：P05/P06 设置消息进入选定 Designer 原会话 |
| T02 | 通过：P06 准备消息触发空闲 Codex 新回合 | 通过：P05 在 PO 放行后触发原 Designer；新 accept 配置未单独复测该格 |
| T03 | 通过：P06 Stop 在 Codex 最后一次生成后接续 | 失败：五次生成窗口采样中，消息到达与原生成截断重合，未满足当前调用正常完成 |
| T04 | 通过：P06 Codex 工具窗口内发信，PostToolUse 交付 | 通过：P06 反向消息在 Designer 后台任务边界进入原会话 |
| T05 | 通过：P06 连续对话覆盖请求、回复、追问、再答 | 通过：同一 P06 连续对话双向往返 |

原型变更或测试失败后，保留之前的记录，说明改变了什么，再复测受影响场景。出现非预期行为时先记录、解释，并将发现带回方案讨论。

## 5. 开测前待补充

- 选定的候选方案、原型位置、两端运行与配置方式。
- 实际配对、发送和回复的操作；模型生成及工具执行场景使用的可重复任务。
- 会话身份、接收入口、状态窗口、调用边界及正文的取证方式。
- 本次观察窗口、等待上限与必要的重跑安排。

这些是使测试可复现的执行细节，随原型就绪后补齐。本文件当前仅记录测试设计，不包含任何已通过的通信结果；初始方案见 TargetMap 第三节，实际实验状态见 [TestResults](TestResults.md)。
