## 1. 方法说明

| 方法 | 用在哪 | 为什么 |
|---|---|---|
| Brainstorming（d.school） | 五视角并行发散，产出 104 条，暂缓评判 | HMW 已就绪，需要大量且差异大的想法；视角即多样性来源 |
| Impose Constraints（d.school） | 给每个发散视角加约束锚点（只用官方原语 / 只挑战默认假设 / 按 HMW 机制穷举） | 约束逼出差异：同一条 HMW 在不同锚点下长出不同的机制 |

| Describe Your Concept（d.school） | 候选统一按"给谁、完成什么、一次往返怎样发生"表述 | 想法必须清楚到能比较、能开测才算候选 |

## 2. 想法池（104 条，按 HMW 归组）

五视角共产出 104 条（官方原语 25 / 组件嫁接 19 / 假设翻转 20 / 寻址与时机枚举 23 / 接续枚举 17）。下表按环节归组保留最具组合价值的约 40 条，每条给名字、一句话本质与主要证据等级；未列出的条目多为已列想法的变体或弱化版。未进入候选的局部想法同样保留，供后续重组。表内辅助标签：**设计产物**＝本设计新约定、无先例可直接验证；**组件级**＝所依赖底层原语已实证而该组合未验；**混合**＝条目内各部分等级不一。

### 2.2 HMW-2 送达与接收时机（四格机制）

**通道腿**（每方向的最强原语）：

| 想法 | 覆盖格 | 证据 |
|---|---|---|
| codex queue 官方通道（Claude→Codex） | 空闲+工作+退出（退出属排除项） | 持久化+resume 消费=实验 E-C；运行中行为=源码级（**忙碌格落点经校验源码核实为回合末交付【校验新增】，见 §4.1**） |
| inbox 命名管道直投（Codex→Claude） | 忙碌格实证（工具间隙入上下文）；空闲格未验 | 实验 E-H；帧格式社区逆向 |
| `claude -p` 一次性 SendMessage 桥（Codex→Claude） | 空闲格实证依据（E-D5 等待态收信转 busy 并回应；空闲态为推断）+通道实证 E-D6 | 实验（两段拼接，端到端待一次确认） |
| SendMessage 官方排队（桥的底层语义） | Claude 忙碌格：官方文档（队列 50/hold 100、环路限流）；"调用边界进入"的字面粒度未证 | 官方文档 |

**时机机制分类**（枚举视角的核心产出）：

| 类别 | 机制 | 覆盖的格 |
|---|---|---|
| 空闲唤醒类 | queue 自动提交（源码级）、管道直投（空闲未验）、-p 桥（空闲实证依据）、会话内定时任务（官方文档：仅空闲触发） | 是——四格中空闲格只能靠这类 |
| 轮中调用边界类 | Codex PostToolUse additionalContext（社区深读，agmsg ≥0.149.1；时序未证）、Claude 管道（实证） | 正对"工作中"格的字面口径 |
| 轮末取件类 | 双端 Stop hook（Codex `{"continue":true}` / Claude `decision:block`） | 只能搭"刚结束一轮"的车，空闲格零覆盖，必须与唤醒类组合 |
| 自醒类 | 会话内 cron 定时查收件箱（官方文档，仅空闲触发）、Monitor 常驻观察（社区深读，空闲消费未证） | 空闲格可用；代价是空轮询模型调用或挂长工具调用 |

**兜底与辅助**：双通道冗余投递+msg_id 去重；心跳状态文件（发送前预判对端，可读性增强非必需）；FileChanged 信号灯（只提示 PO，输出不进上下文，不构成送达机制）；ultracode 指针唤醒架构（唤醒永不携正文+COMMIT-first+静默降级拉取，社区深读）。

**负面清单**（设计排除依据，全部官方文档级/实验级）：`--resume` 对运行中会话产生分叉副本（E-D3/D4，触约束 2）；MCP 桥=委派新实例非触达既有会话（E-G）；纯文件投递无取件机制=消息不进上下文；FileChanged/UserPromptSubmit 独用不满足空闲格（门控/不进上下文）；hooks 无法唤醒已空闲会话；按键注入冒充用户输入（强烈不推荐，触开放范围）。

### 2.4 整段策略想法（供组合）

直通桥 v0（研究推荐 P1 的 Ideate 版）、零配置纯 CLI 桥（即查即用）、全自动往返桥（notify+Stop 钩子驱动，环路风险最高）、常驻邮差（通道逻辑收敛一处，Windows 守护进程管理是负担）、定时邮差（计划任务离散触发，最坏延迟=间隔）、潮汐轮次（挑战即时性：准同步书信制，时序合规但体感待验）、单文件总线+双注入器（总线对称、注入异构可替换）、信纸协议（协议住进项目指令文件，消息保持纯内容——三候选共用的知识层）。

## 3. 候选方案（三套，校验修正已吸收）

三套候选是同一零件库的三种组装哲学，不是三个对立产品。X→C 方向三套已实质收敛（管道/`-p` 桥按状态分工），实质差异集中在：C→X 方向押注、寻址设施、连续性载体、部件数与成本。

### 候选 A：官方双邮路（名字即地址）——极简

**一句话**：不修新路，只用两条官方邮路——去程 `codex queue`、回程 `claude -p` 一次性 SendMessage 中继；零 hook、零常驻进程、零共享文件，全部部件 = 两条一行命令 + 项目指令里一段协议。

**四格**（校验修正后）：

| 格 | 机制 | 证据（修正后） |
|---|---|---|
| C→X 空闲 | queue 持久化，线程转 idle 自动提交开新回合 | 源码+README（出处为 app-server README，TUI 属外推）【校验新增】；失败则此格无已知原语 |
| C→X 工作 | queue FIFO 排队至回合边界 | **源码核实=回合末交付**【校验新增】——宽窄口径需 PO 前置裁定（§4.1） |
| X→C 空闲 | `claude -p` 中继 → SendMessage 收信触发新调用 | 实验（E-D6+E-D5 两段拼接，端到端待一次确认；两实验均在 `--bg` 会话，交互式为文档级） |
| X→C 工作 | SendMessage 官方排队语义 | 官方文档；"调用边界进入"的字面粒度未证（E-H 管道为旁证） |

**往返**：DEV 按 `--thread CTC-SM` 直投（名字即地址）；SM 在自己会话组织回应后用 `claude -p` 中继送回；连续性靠信封（from/thread/msg#）+ 短线程 ID + 1:1 自然衔接，无台账。追问=同线程号再走一圈。**校验补入的必要规则**：DEV 收到的消息其通道级发送者显示为中继的自动名——回复必须按正文信封走 queue，禁止用通道回复地址（指向已死的中继进程）。
**配置成本**：PO 两个动作（`/rename` + `claude -n`），Developer 把约 15–20 行协议写进两个指令文件。约 30 分钟。
**校验修正要点**：①失效条件里"Claude 名不持久"是错的——官方文档明示按名可 resume【校验新增】；②hold 判决表确定化后，DEV 会话权限形态成为设计变量：常规权限 + 裸 `claude -p` 中继 = 自动投递零配置；若 DEV 用 bypass 则需 `crossSessionInbound: "accept"` 一行，否则消息被 hold，而中继发送后即退出、无人确认对话框，过期即静默丢（§4.4）；③新增失效模式：SM 回合被 Esc 打断后队列暂停、消息无限期静默滞留（§4.3）；④"无官方命令列出运行中 Codex 会话"不准确——`codex agents` 存在（本机 help 实跑【校验新增】），但是交互式浏览器且依赖的 shared daemon 在 Windows 可用性未验。
**取舍**：用"每条回程一次中继模型调用"换零文件零 hook；把成败押在 queue 单组件上（不确定性收敛，第一天可测掉）；连续性押模型纪律，压缩免疫后置 v1；名字无防护（单机单用户 1:1 威胁模型下接受）。

### 候选 B：指针驿站（Pointer-Post 双原生腿桥）——复用

**一句话**：热路径只用两条已实证官方原语，健壮性模式全部移植成熟社区组件——唤醒永不携正文（ultracode）、游标幂等读+冷却（agmsg）、三级寻址+勿信 body from（chillacks）、SessionStart 落卡姿势（codex-plugin-cc）。

**四格**（校验修正后）：C→X 两格同候选 A（queue 指针唤醒，同样的两处押注与口径裁定）；X→C **修正为按接收方状态分路**（校验发现原设计"管道优先、失败降级 -p"存在静默死亡路径：管道对空闲会话可能连接成功、auth 通过、消息被接受、但永不唤醒，无错误信号、降级不触发）——忙碌→管道直投（E-H 实证对位格），空闲→`-p` 桥（E-D5/D6 实证对位格）；状态输入用 `agents --json`，**但本机实跑仅见后台会话**【校验新增】，交互式 DEV 的可见性需实测，不可见时退为"管道投递后 N 秒校验 idle→busy 跃迁，未跃迁自动补发 -p"。
**往返**：发送=两步（COMMIT-first 正文落 `outbox-<sender>.jsonl` 每发送者一文件 → queue/管道只投一行唤醒语）；接收方被唤醒后按协议自跑 `bridge.ps1 read`，正文经自己的工具调用进入原会话上下文（约束 3 的"实际接收行为"）；连续性锚在共享台账+信封，压缩后重读台账重锚。
**校验修正要点**：①名片劫持漏洞——项目级 SessionStart hook 无条件写卡，本仓库内任何后启动的 Claude 会话都会覆写名片冒充 CTC-DEV，唤醒会送达替代会话（触约束 2）；修正为"仅在会话注册名为 CTC-DEV 时写卡 + 发送前核验卡上 sessionId 与注册名一致，不一致拒发"；②补上缺失的命名前置（`claude -n` / 会话内命名），否则按名寻址与 `-p` 兜底双双落空；③"hooks 可读 env 中 SOCKET/TOKEN"从实验实证降为记录断言（E-H 实证的是 shell 子进程路径；hook 路径待一次微实测）；④token 明文落盘是研究建议+PO 授权项（Research 6.3-q2），非实验要求；可考虑 DPAPI 加密替代明文；⑤queue 对已退出线程的唤醒语会在日后 resume 时逐字涌入（E-C 实证行为的副作用）——发送前活性预判失败即硬失败回显，不留静默滞留。
**配置成本**：Developer 约 0.5–1 天（单文件 `bridge.ps1` 200–300 行 + Claude 侧两个 hook + 协议双文件），PO 约 5 分钟习惯成本。
**取舍**：指针制对正文尺寸/转写免疫（帧格式并不免疫，管道腿仍暴露于社区逆向帧）；接受一跳取件延迟与模型服从性押注；放弃常驻邮差与统一总线的优雅换约束 2 干净（只有一次性信使）。

### 候选 C：挂号信桥（先落账、指针唤醒、双邮路降级）——可靠

**一句话**：像挂号信——正文先落账（零丢失），通道只送取件通知；每格用该格证据最强的腿，任一腿失败沿预写降级链走，每次尝试写投递日志；防环四重保险。

**四格**：同 B 的修正（状态分路 X→C；queue 两格同押注+裁定）；C→X 忙碌格另有 Stop hook 轮末取件兜底（注意：轮末取件同受 §4.1 严口径约束——它把消息放到回合边界，救不了"原任务未完成时的调用边界注入"）、X→C 两腿全败时有账本+Stop 补收——**但"静默丢失被排除"的承诺要打折**：空闲且两腿全败时正文在账内无限期滞留（零丢失成立、投递时效无界），最后保险"定时自醒 sweeper"是否纳入交 PO。

**往返**：配对时 PO 把两端精确身份手抄进 pair.json。DEV 提问：`send-to-sm.ps1` 第一步把消息（conv_id/序号/正文/背景指针）COMMIT-first 追加进 ledger.jsonl，第二步 `codex queue` 只投指针唤醒；SM 按四格腿之一被唤醒后，在自己的下一次模型调用里跑读账命令，正文经其工具输出进入原会话上下文，结合当前任务自行判断处理与回应时机；SM 回应走 `send-to-dev.ps1` 同路反向（先落账，再按 DEV 状态选管道或 `-p` 桥，两腿失败留账待 Stop 补收）；DEV 收到后追问＝同 conv_id 再走一圈，上下文压缩后按指令重读台账重锚。

**寻址**：pair.json 一次性快照（**校验修正：v0 默认路径=PO 手抄两端身份**，SessionStart 写卡与自报名片列为增强项——原叙事把兜底写成了主路径）；Claude 名与 UUID 双保险。
**连续性**：台账+线程文件两级落盘、round cap/冷却/无纯确认/显式关闭四重防环；**校验补入**：Stop 取件腿需自我熔断（同一指针最多 `decision:block` 两次即放行并告警，防"阻断→续跑→未取到→再阻断"自环烧调用——agmsg #1045 教训映射到自家腿）；消息头"已读至 msg_id=X"的搭车确认**属开放范围"送达状态反馈"**，是否作为产品能力交 PO。
**校验修正要点**：①`agents --json` 的 busy/idle 在 `status` 字段非 `state`（实验记录核对）；②"-p 桥忙碌时按调用边界进入"降为未验证推测；③"exec resume 对运行中会话触约束 2"的排除本身未坐实（对已退出会话才是实证），补一个 5 分钟实验前表述为"无已知备用原语"；④成本对照"一小时"无出处（研究口径是"一天内"）；⑤交互式 `claude -n` 命名未测，启动纪律改用会话内 `/rename` 更稳。
**配置成本**：约 6–7 个部件（台账/游标/投递日志/双端 Stop hook/双发送脚本/卡片），首通半天以上。
**取舍**：部件换可追溯；指针换尺寸免疫；付费走实证腿（空闲用 `-p` 而非未验管道）；放弃 notify 自动回投换对话自主权；重启即重配对（寻址维护挡在轮外）。

## 4. 跨候选共性发现与新事实（对抗校验产出）

### 4.1 【需 PO 前置裁定】queue 忙碌格 = 回合末交付，与接收规则字面口径冲突

校验 agent 逐环读取 openai/codex@6af3454 `codex-rs/ext/queue/src/service.rs`：忙碌中（AgentStatus::Running）dispatch 直接 return，投递唯一入口是回合结束（on_thread_idle → start_turn_if_idle）——消息**只在整回合结束后作为新回合启动**，回合中途的任何调用边界都不注入。README 明文"the server starts the next queued turn when the thread becomes idle"。对照 PO 口径"当前模型调用及其工具执行结束后、下一次模型调用前进入上下文，**原任务此时可以尚未完成**"（Synthesis）：字面口径下 queue 不合规。**三套候选的 C→X 方向全部押注 queue，此裁定先于原型**：
- 宽口径（回合边界也算"相邻调用之间"，接受"原任务已完成"）：queue 单通道即可，三候选照建；
- 严口径（必须原任务未完成时于调用边界注入）：Codex 侧唯一已知调用边界机制是 PostToolUse additionalContext（社区深读级，agmsg ≥0.149.1 门控已满足；时序未证，且 Windows 有 #1015 登录 shell 污染前科，须改 PowerShell 原生实现）——从备件升必需件。

### 4.2 Codex 空闲格是三候选共同的结构性单点

"thread becomes idle 自动提交"出处是 **app-server README**【校验新增】——TUI 是否同行为属外推，源码级+文档级双重未实测。Codex 空闲会话无任何 hooks 事件、notify 单向出站、无管道接口：**queue 是唯一已知空闲唤醒原语，无备用**。若实测失败，该格无已知解，方向回炉。这把"queue→运行中 TUI 三态实测"顶到验证清单第一位。

### 4.3 queue 的两个新行为（一好一坏，均 README 明文+源码佐证【校验新增】）

坏：**被中断的回合会暂停队列**（含 resume 之后）——SM 被 Esc 打断后，后续消息无限期静默滞留，直到手动启动队头或任一新回合正常完成。须写进失效条件、测试场景加"打断后投递"用例、协议加一行"SM 被打断后先看 /queue"指引。好：**完成和失败的回合都会自动启动下一条排队消息**——网关 503 不滞留队列，可靠性利好。

### 4.4 hold 审批从"待复验"变为确定性设计变量【校验新增：官方文档判决表】

按双方权限类配对判决：接收方 bypass + 发送方 prompting ⇒ 全部 hold，对话框 5 分钟过期即丢弃。"发送方零感知"只成立于非交互中继（`-p` 发完即退出、无人确认对话框）；交互式同机发送方会收到 hold 通知与过期/拒绝的后续通知，后台会话未 attach 时对话框不过期、attach 后再计时。常规权限收件 + 裸 `claude -p` 中继（同为 prompting 类）⇒ 自动投递。设计含义：**DEV 会话权限形态是显式设计变量**——保持常规权限（零配置自动收）或显式 `crossSessionInbound: "accept"`（一行 settings），二者择一；测试须覆盖"hold+过期+中继已退出=静默丢失"场景。

### 4.5 交互式会话的证据是薄的（E-D 系实验全在 `--bg` 会话上做）

【校验新增】本机实跑 `claude agents --json` **仅列出后台会话**（help 亦写"Manage background agents"）——交互式 DEV 能否被枚举未验证，直接影响三处：B/C 的状态分路输入、A 的"免费活性校验"、B 的反劫持核验（"卡上 sessionId 与注册名一致"同样以可见性为输入，交互式不可见时需降级为文件指纹或 PO 目检）。同时 E-D1/D2/D5/D6 的命名/枚举/收信证据对交互式会话均为文档级外推。补法：一个"交互式 `claude -n` 会话的一次 SendMessage 收信+可见性"实验，同时观察 agents --json 能否列出它。另：Claude 会话名跨 resume 持久（官方文档【校验新增】，比候选假设更稳）；`codex agents` 命令存在（本机 help 实跑【校验新增】），交互式浏览器，Windows daemon 可用性未验；queue 按名寻址有二进制级文档（`codex-rs/cli/src/queue_cmd.rs` help 明文"Session UUID or exact session name"【校验新增】），重名解析行为仍未知。

## 6. 推荐（供 PO 与 SM 讨论，不替代拍板）

**倾向**：以候选 A 为第一周测试载具，把 B/C 当部件库按需叠加——A 的"协议段+信封+线程头"本就是三候选共享底座；B 的状态分路修正（busy→管道、idle→`-p` 桥）值得吸收进 A 的 v0.1——注意代价是每次发送多一步 `agents --json` 预检或投递后跃迁校验，与 A 的零文件立场略有张力，故列为 v0.1 可选件而非 v0 必装；C 的台账/降级链/投递日志在往返变长或消息变重要时再加。理由：原型原则是学习速度优先——A 部件最少、把全部不确定性收敛到 queue 单组件，且 §4 的裁定与实测结果会直接决定 B/C 的哪些部件是必需的；先裁定后搭建，比预装一堆机制再拆便宜。

**前置裁定（PO，先于原型搭建）**：
1. 忙碌格宽窄口径（§4.1）——决定 queue 单通道够不够；
2. DEV 会话权限形态（§4.4）——常规权限 or `crossSessionInbound: "accept"`；
3. 开放范围四项的入轮/出轮，至少裁"送达状态反馈要不要成为产品能力"与"接收失败处理纳入深度"；
4. 确认"一次性送信中继只送信、不算替代会话"的口径解释（三候选回程腿的合规基础；TargetMap 原文支持但未逐字明示）。

**最值得验证的问题（按优先序，均为分钟级协同实验）**：
1. queue→运行中 TUI 三态：空闲自动提交？忙碌落点（校验源码结论的真机确认）？中断后暂停？——Claude→Codex 方向的生死点；
2. 管道直投→空闲 Claude 会话是否触发新模型调用——若是，X→C 两格统一走管道，每条省一次中继模型调用；
3. 交互式 `claude -n` 会话：SendMessage 收信 + `agents --json` 可见性——决定状态分路的输入；
4. hold/权限形态实测（对照 §4.4 判决表）；
5. queue 按名寻址 + 重名解析行为（含 Codex 会话名唯一性范围）。
