## 1. PO 已确认的方向

### 协作范围

长期希望 PO、Codex 与 Claude Code 能作为分工清楚的团队共同推进项目。本轮聚焦 Codex 与 Claude Code 的独立会话之间主动互发工作消息。

- 各自会话保持独立，另一方不会自动知晓当前讨论；发送消息时提供的内容，以及接收方能读取的相关材料，构成其理解问题的依据。
- 双方都可以主动发起消息。例如 Developer 遇到困惑向 Scrum Master 求助，或 Scrum Master 就讨论中的技术问题向 Developer 征求意见。
- PO 可以继续在任一会话参与讨论。该会话向另一方发送问题与必要背景，收到意见后继续与 PO 讨论。
- 共同讨论现场不在当前冲刺范围内。共享讨论文件是候选记录方式，其必要性尚未验证。
- PO 决定价值方向与优先级；Developer 负责实现方式。Codex 通常承担 Scrum Master，Claude Code 通常承担 Developer 或其他角色。

### 本轮 Target 与成功标准

PO 已确认圈定“发送问题到反馈回到原会话”，包含必要的追问往返。本轮以两个现有会话能够双向互传消息、连续对话为成功标准，通过一系列通信测试判断，先验证基础能力，再由 Scrum 实现骨架；后续功能按需要通过新的工作项与 PR 迭代。

主要选择 DesignMap Q1 与 Q3 的多轮通信部分。反馈质量、完整开发任务交付及长期减负效果保留为观察项，不增加本轮验收门槛。目标详情、HMW、方案、原型与测试结论集中在 [TargetMap](../cross-session-agent-messaging/TargetMap.md)。

### 消息接收与处理

以下是已确认的期望行为，是否能在当前工具中完整实现仍需验证。

| 接收方状态 | 期望行为 |
|---|---|
| 空闲，无新刺激 | 保持空闲 |
| 空闲，收到另一方消息 | 消息作为外部刺激触发下一次模型调用 |
| 正在工作，收到消息 | 消息先排队；当前模型调用及其工具执行结束后，在下一次模型调用前加入上下文 |
| 已获得消息上下文 | 接收方结合当前任务判断如何处理、何时回应，以及是否调整工作 |

接收边界位于相邻模型调用之间，原任务此时可以尚未完成。消息进入上下文不意味着强制切换任务。该接收规则适用于两个方向，包括回复。

## 2. 研究提供的证据

下表依据 Developer 交付的原始研究记录整理，Codex 在研究讨论阶段未复跑这些实验；后续原型实验在本节补记中单列。实验环境和适用版本以各自记录为准，不能直接推广到所有工具版本或运行形态。

| 发现 | 证据及边界 | 对当前设计的意义 |
|---|---|---|
| 向 Codex 排队的消息可持久化并在恢复同一线程后被读取 | 实验 E-C；接收方是已退出或未加载的会话 | 提供候选通道，尚未证明工作中的接收时机 |
| Codex 运行中 TUI 的队列消费存在源码依据 | 研究报告 Q1 与第 4.1 节；原研究阶段的运行中真机行为未验证，后续见下方 P01/P02 补记 | 需检查实际调用边界，不能仅凭排队成功或轮询间隔认定满足需求 |
| 一次性 Claude 会话可用 SendMessage 向另一运行中 Claude 会话发信 | 实验 E-D5/E-D6；目标会话收到探针 | 提供从外部进程触达 Claude 现有会话的候选路径 |
| Windows 命名管道可向运行中 Claude 会话直接投递消息 | 实验 E-H；观察到工具调用间隙收信，使用特定版本及权限条件 | 与所需接收时机有关，但帧格式、权限条件及重启后的行为仍需确认 |
| 已调查仓库提供消息桥、收件箱、会话寻址等参考 | 研究报告第 4.2、4.3 节（含 2026-09-06 补扫后的 agmsg/let-them-talk 等，深读见 4.3-D） | 可以支持复用或适配方案比较；尚未选定采用某个仓库或机制 |

### 对报告概括的校正

- “双端运行中会话均已实证”对原始研究而言概括过强：Codex 侧当时实验证实的是排队后恢复消费。后续 P01/P02 补足了部分运行中证据，但完整接收能力仍未满足，Q1 保持开放。
- “未找到适配当前条件的现成方案”只适用于已调查范围，不能推导为所有可能方案均不存在。
- 【Developer 补记，2026-09-06】该限定当日即被证实必要：PO 指出 agmsg 后，报告经词族补扫修订（见 [Research.md](Research.md) 4.2 与 4.3-D，提交 `a425c35`）——跨工具互发消息的现成品确实存在（agmsg 1.5k★/MIT、let-them-talk 53★/BSL 1.1 等四条独立路线），评估结论为 Windows+双工具+PO 组合各有硬伤（agmsg 的 Codex Windows 收信 turn-only 且空闲不达，弱于已验证的官方 `codex queue` 路径），报告推荐仍为自建优先。报告初稿中”没有任何主流现成品”的旧概括已按此改写。
- “必须自建共享讨论层”及“共享讨论成为当前核心问题”属于报告建议。本轮 PO 已明确共同讨论现场留待未来，当前重点是独立会话中的消息往返。
- “约百行直通桥”、具体消息延迟指标和插件组合均为研究建议。它们尚未成为已确认的实现方案或验收标准。

### 原型实验补记（2026-09-06）

PO 与 Codex 在 Windows / Codex CLI 0.153.4 的同一运行中 TUI 原会话完成了两次通道实验，详见 [TestResults](../cross-session-agent-messaging/test/TestResults.md)。P01 由外部脚本通过 queue 唤起空闲会话，正文进入原会话并得到正确标记的回复。P02 在工具执行期间投递成功，但正文直到原工作回合结束后才成为新回合输入，未满足工具结束后的首次调用接收要求。

这两次实验支持保留 queue 的空闲唤起作用，并继续验证方案中的同步 Hook 是否能补足忙碌接收。P01/P02 的发送方均为普通脚本，Claude 方向和真实双向连续往返尚未因此获得通过结论。

随后 P03 在重新加载配置后验证了同步 `PostToolUse.additionalContext`：Hook 生成的随机正文先成为原会话上下文，工具后的首次续接即输出正确标记，再继续完成原工作。Hook 单项注入已通过；早期缺少 Hook 执行证据的运行仍保留为无法判定。配置恢复只是准备，测试正文在恢复后的工具执行结束时新生成。本次没有验证实际外部来信、收件箱消费或 queue 与 Hook 的组合，完整接收规则仍需继续实测。

2026-09-07 的 P04 将正文来源换成外部脚本：正文在工具执行期间写入临时文件，工具完成后由同步 Hook 注入，首次续接输出正确标记，再继续完成原工作，定向实验通过。首轮误用 P02 queue 通道的混测记录保留。至此支持 Codex 空闲唤起与工具后读取外部正文的单项能力；两种入口的组合、生成末尾接收及真实 Claude 往返仍待验证。

同日 P05 完成选定 Codex 与 Designer 原会话的一次真实往返，条件是 PO 批准了 Claude 侧暂存的消息。日志明确说明发送方未声明权限模式、接收会话跳过权限提示，因此最初未把正文交给模型；放行后，Designer 原会话执行 queue 回信，Codex 原会话收到并确认。该结果证明了受上述接收条件约束的双向通道，尚未证明无需逐条批准的自动收信。PO 已决定暂时保留现有接收审批，原生设置是否修改以后再定，不制作自动批准机制，也不把设置调整作为继续原型的前置项。后续仍需验证连续追问及各状态的完整组合，审批作为实验条件记录，细节见 TestResults 的 P05 记录。

### 2026-09-08 原型补记与校正

组合原型在固定原会话间完成 T01–T05 双方向验证。Claude→Codex 采用 queue 唤醒与 `UserPromptSubmit`/`PostToolUse`/`Stop` Hook；Codex→Claude 采用原生命名管道。早期 T03 方向 B 的五次失败被校正：发送器误把普通消息固定为 `priority=now`，该值是显式抢占语义，会截断当前流式输出。协议源码确认 `next` 才是普通消息默认语义。

修正后的运行 `d93b861e-5703-4cab-b196-71ad1c4feaa0` 使用 `priority=next`：消息在 Claude 生成期间到达，当前输出完整结束，随后进入下一次上下文并报告正确标记。因此基础通信 Target 在记录环境下达到原型级通过。结论限于单对会话、短文本、串行投递和记录版本；会话重启恢复、并发、持久投递、送达回执和网关稳定性移交后续工程工作。详细证据见 [TestResults](../cross-session-agent-messaging/test/TestResults.md)。

## 3. 带入后续设计与验证的事项

| 对应问题 | 仍需学习什么 |
|---|---|
| Q1：送达与接收时机 | 原型已验证空闲、生成中、工具边界和连续往返；产品化仍需覆盖并发、失效恢复、端点重建和长期可靠性 |
| Q2：理解问题 | 消息携带的信息与共享材料是否足够，接收方能否正确理解请求 |
| Q3：多轮往返 | 独立会话能否清楚关联问题、回复、追问与结论，是否确实需要额外记录方式 |
| Q4：接续行动 | 收到消息后能否结合当前任务合理处理，并让正确角色继续工作或向 PO 提出待决问题 |
| Q5：PO 体验 | 是否减少人工搬运消息及补充背景的负担，同时保留 PO 对关键讨论和进展的掌握 |

本轮已选定 Q1 与 Q3 的通信部分，其他问题保留为后续观察和学习方向。具体传输方式、会话寻址、版本兼容和配置方式由 Developer 在方案探索中评估。会话未运行、重启或接收失败时的行为仍待后续明确。官方插件、远程参与和仓库 remote 等扩展建议不构成本轮研究收束的前置条件。

## 4. 阶段结论与文档维护

研究与专家讨论确认了范围和接收规则；组合原型随后完成 T01–T05 双方向验证，基础通信能力在记录环境下达到原型级通过。设计冲刺可以收口，并将骨架实现、恢复、并发和可靠性转入 Scrum Backlog。
