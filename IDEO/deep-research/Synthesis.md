## 1. PO 已确认的方向

### 协作范围

长期希望 PO、Codex 与 Claude Code 能作为分工清楚的团队共同推进项目。本轮聚焦 Codex 与 Claude Code 的独立会话之间主动互发工作消息。

- 各自会话保持独立，另一方不会自动知晓当前讨论；发送消息时提供的内容，以及接收方能读取的相关材料，构成其理解问题的依据。
- 双方都可以主动发起消息。例如 Developer 遇到困惑向 Scrum Master 求助，或 Scrum Master 就讨论中的技术问题向 Developer 征求意见。
- PO 可以继续在任一会话参与讨论。该会话向另一方发送问题与必要背景，收到意见后继续与 PO 讨论。
- 共同讨论现场不在当前冲刺范围内。共享讨论文件是候选记录方式，其必要性尚未验证。
- PO 决定价值方向与优先级；Developer 负责实现方式。Codex 通常承担 Scrum Master，Claude Code 通常承担 Developer 或其他角色。

### 消息接收与处理

以下是已确认的期望行为，是否能在当前工具中完整实现仍需验证。

| 接收方状态 | 期望行为 |
|---|---|
| 空闲，无新刺激 | 保持空闲 |
| 空闲，收到另一方消息 | 消息作为外部刺激触发下一次模型调用 |
| 正在工作，收到消息 | 消息先排队；当前模型调用及其工具执行结束后，在下一次模型调用前加入上下文 |
| 已获得消息上下文 | 接收方结合当前任务判断如何处理、何时回应，以及是否调整工作 |

接收边界位于相邻模型调用之间，原任务此时可以尚未完成。消息进入上下文不意味着强制切换任务。该接收规则适用于两个方向，包括回复。

## 2. 研究提供的证据

本节依据 Developer 交付的记录整理；Codex 在本轮讨论中未复跑实验。实验环境和适用版本以原报告为准，不能直接推广到所有工具版本或运行形态。

| 发现 | 证据及边界 | 对当前设计的意义 |
|---|---|---|
| 向 Codex 排队的消息可持久化并在恢复同一线程后被读取 | 实验 E-C；接收方是已退出或未加载的会话 | 提供候选通道，尚未证明工作中的接收时机 |
| Codex 运行中 TUI 的队列消费存在源码依据 | 研究报告 Q1 与第 4.1 节；运行中真机行为仍待验证 | 需检查实际调用边界，不能仅凭排队成功或轮询间隔认定满足需求 |
| 一次性 Claude 会话可用 SendMessage 向另一运行中 Claude 会话发信 | 实验 E-D5/E-D6；目标会话收到探针 | 提供从外部进程触达 Claude 现有会话的候选路径 |
| Windows 命名管道可向运行中 Claude 会话直接投递消息 | 实验 E-H；观察到工具调用间隙收信，使用特定版本及权限条件 | 与所需接收时机有关，但帧格式、权限条件及重启后的行为仍需确认 |
| 已调查仓库提供消息桥、收件箱、会话寻址等参考 | 研究报告第 4.2、4.3 节（含 2026-09-06 补扫后的 agmsg/let-them-talk 等，深读见 4.3-D） | 可以支持复用或适配方案比较；尚未选定采用某个仓库或机制 |

### 对报告概括的校正

- “双端运行中会话均已实证”概括过强：Codex 侧实验证实的是排队后恢复消费，运行中行为仍有验证缺口。Q1 保持开放。
- “未找到适配当前条件的现成方案”只适用于已调查范围，不能推导为所有可能方案均不存在。
- 【Developer 补记，2026-09-06】该限定当日即被证实必要：PO 指出 agmsg 后，报告经词族补扫修订（见 [Research.md](Research.md) 4.2 与 4.3-D，提交 `a425c35`）——跨工具互发消息的现成品确实存在（agmsg 1.5k★/MIT、let-them-talk 53★/BSL 1.1 等四条独立路线），评估结论为 Windows+双工具+PO 组合各有硬伤（agmsg 的 Codex Windows 收信 turn-only 且空闲不达，弱于已验证的官方 `codex queue` 路径），报告推荐仍为自建优先。报告初稿中”没有任何主流现成品”的旧概括已按此改写。
- “必须自建共享讨论层”及“共享讨论成为当前核心问题”属于报告建议。本轮 PO 已明确共同讨论现场留待未来，当前重点是独立会话中的消息往返。
- “约百行直通桥”、具体消息延迟指标和插件组合均为研究建议。它们尚未成为已确认的实现方案或验收标准。

## 3. 带入后续设计与验证的事项

| 对应问题 | 仍需学习什么 |
|---|---|
| Q1：送达与接收时机 | 两个方向均应验证空闲收信触发调用，以及工作中在当前调用和工具结束后、下一次调用前获得消息。进入队列、被模型看到和完成回应需分别观察 |
| Q2：理解问题 | 消息携带的信息与共享材料是否足够，接收方能否正确理解请求 |
| Q3：多轮往返 | 独立会话能否清楚关联问题、回复、追问与结论，是否确实需要额外记录方式 |
| Q4：接续行动 | 收到消息后能否结合当前任务合理处理，并让正确角色继续工作或向 PO 提出待决问题 |
| Q5：PO 体验 | 是否减少人工搬运消息及补充背景的负担，同时保留 PO 对关键讨论和进展的掌握 |

具体传输方式、会话寻址、版本兼容和配置方式在选定验证重点后由 Developer 评估。会话未运行、重启或接收失败时的行为仍待后续明确。官方插件、远程参与和仓库 remote 等扩展建议不构成本轮研究收束的前置条件。

## 4. 阶段结论与文档维护

本轮研究已提供候选技术路径、实验记录及明确缺口；专家讨论已确认当前范围和接收规则。这些材料足以进入 Map，并在其基础上由 PO 选择 Target。完整通信能力和减负效果尚待原型验证。

- `Research.md` 与实验记录保存原始研究发现及其来源。
- 本文件集中保存研究与专家讨论的综合判断；后续证据或 PO 决定改变结论时，在这里更新并注明依据。
- `../DesignMap.md` 保存当前工作中的挑战、目标、问题、Map 和待确定的 Target，通过链接追溯背景。
