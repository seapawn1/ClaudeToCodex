# 深度研究综合结论

- 阶段：Design Sprint 已收口，准备移交 Scrum。
- 日期：2026-09-06 至 2026-09-08。
- 结论等级：基础双向通信在记录的原型环境中成立；长期可靠性、并发和自动恢复尚未验证。
- 原始材料：design-sprint 分支历史中的 `IDEO/deep-research/`；收口 tag 见 `design-sprint-closed`。

## 1. 已确认的问题与接收规则

长期方向是让 PO、Codex 与 Claude Code 形成分工清楚的协作团队。本轮只研究两个独立现有会话之间的主动工作消息往来：任何一方都可以发起，接收方在自己的原会话中获知消息，PO 不再代为搬运正文。

本轮验收不要求反馈质量、完整开发任务交付或长期减负效果；这些保留为观察项。基础通信的接收规则如下：

| 接收方状态 | 期望行为 |
|---|---|
| 空闲且无新刺激 | 保持空闲 |
| 空闲时收到消息 | 消息作为外部刺激触发下一次模型调用 |
| 正在工作中收到消息 | 当前模型调用及其工具执行先正常结束，消息在下一次模型调用前进入上下文 |
| 已获得消息上下文 | 接收方结合当前任务判断处理、回应和是否调整工作 |

消息进入上下文不等于强制切换任务。该规则适用于两个方向和所有回复。

## 2. 研究发现与证据边界

| 发现 | 证据边界 | 对方案的影响 |
|---|---|---|
| Codex queue 能把消息投给指定线程并唤醒原会话 | 原型实测空闲唤醒、生成末尾与工具边界组合路径；结论限于记录版本和 Windows 环境 | 作为 Claude→Codex 的唤醒信号，不单独承担正文交付 |
| Codex hook 可在 `UserPromptSubmit`、`PostToolUse`、`Stop` 边界注入待收正文 | 原型实测三条入口，并通过消费记录抑制旧唤醒 | 作为 Codex 原会话的正文交付入口 |
| Claude 原生命名管道可向选定会话投递消息 | 原型实测短文本、串行消息和记录版本；令牌与端点有效期依赖进程 | 作为 Codex→Claude 的普通消息通道 |
| Claude 消息优先级 `next`、`later`、`now` 语义不同 | 源码与实测确认：`next` 为普通消息；`now` 为抢占；`later` 尚未现场实测 | 普通协作固定 `next`，`now` 只保留为显式紧急模式 |
| 现成跨工具消息项目提供可借鉴组件 | 研究比较 agmsg、let-them-talk、Claude/Codex 官方原语等；未发现完全覆盖 Windows、双工具、原会话与 PO 场景的方案 | 选择自建最小桥，而不是整装引入第三方系统 |
| resume 可能产生分叉或替代会话 | 实验记录确认存在该风险 | 验收必须核对原会话身份，副本收信不算通过 |

## 3. 设计结论

研究阶段曾存在一个关键校正：把普通 Claude 消息误发为 `priority=now`，导致当前生成被截断。后续确认 `next` 才是普通消息语义。修正后的运行 `d93b861e-5703-4cab-b196-71ad1c4feaa0` 证明：消息在 Claude 长文本生成期间到达，当前输出完整结束，随后进入下一次上下文并报告正确标记。

因此，设计冲刺选定「最小原生双向桥」：Claude→Codex 使用本地待收 inbox、queue 唤醒和 Codex hooks；Codex→Claude 使用 Claude 原生命名管道与 `priority=next`。这不是对第三方方案的否定，而是当前证据下部件最少、可控性最高的起点。

## 4. 仍需 Scrum 学习与工程化

以下问题不属于设计结论，进入 Product Backlog 后按价值排序：

- 配对、端点登记与配置产品化。
- 会话重启、进程回收和端点重建。
- 并发消息、长文本、失败重试与持久台账。
- 送达回执、失败可见性和接收方体验。
- 来源校验、权限模式与安全边界。
- `later` 优先级、更多工具版本和长期运行稳定性。
- 共同讨论现场、多会话协作和远程协作形态。

Scrum 不应把这些项一次性并入首个 Increment。首个骨架应优先复现已验证的双向通信路径，再用自动化回归和端到端 smoke scenario 保护行为。
